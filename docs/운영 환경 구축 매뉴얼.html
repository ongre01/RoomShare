운영 구축 개요. 실제 명령은 RS-008 배포·복구 실행서, 환경별 판정은 QA 보고서를 따른다. 로컬 시험은 OCI 배포나 공개 승인이 아니다.

1. 적용 범위와 구축 전 결정

RoomShare는 원룸 한 개를 한국 시간의 달력 날짜(YYYY-MM-DD) 단위로 예약하는 FastAPI·SQLite 서비스다. 사용자와 관리자는 서로 다른 HTTPS 호스트를 사용한다. 관리자 주소 분리만으로 접근을 허용하지 않는다. 운영 관리자 호스트는 mTLS로 보호하고, 앱의 프록시 검증과 Origin·CSRF 검사도 함께 사용한다. 사설망 방식으로 변경하려면 별도 설계와 검증이 필요하다.

구축 전에 운영자가 아래 값을 확정하고 기록한다. 예시 도메인과 1 GB RAM 목표는 확정된 운영 값이 아니다.

항목 확인할 내용
서버 승인된 OCI VM의 Ubuntu/Python 버전, RAM·디스크 여유, 비용 한도, 관리 권한
주소 사용자·관리자 각각의 실제 DNS 이름과 A/AAAA 레코드
네트워크 443 공개, 80은 인증서 검증 또는 HTTPS 이동에 필요한 경우만 사용, SSH는 관리 IP로 제한, 앱 포트 8000은 외부 차단
인증서 두 호스트의 서버 TLS 인증서, 관리자 전용 신뢰 CA 및 클라이언트 인증서 발급·갱신·폐기 담당자
정책 예약 가능 기간·접근 범위·요청 제한·백업 주기/보존 기간·복구 목표·개인정보 처리 방침
검증 환경 실제 운영 데이터와 분리된 Ubuntu 스테이징, 테스트 CA, 외부 접속 시험용 클라이언트

정책의 현재 임시값은 DECISIONS, 릴리스 기준은 TEST_PLAN을 따른다. 실제 OCI 네트워크·DNS·인증서·기기 검증과 운영자 승인 전에는 공개하지 않는다.

2. 파일 배치와 권한

경로 용도 권한 원칙
/opt/roomshare 검증된 릴리스 소스와 .venv 배포 관리자 소유, 서비스 계정은 읽기·실행만
/var/lib/roomshare SQLite DB와 WAL·SHM 전용 비권한 서비스 계정만 쓰기
/etc/roomshare/roomshare.env systemd가 읽는 운영 설정 관리자만 수정, 다른 사용자에게 공개 금지
별도 백업 위치 검증된 DB 스냅샷 DB와 분리, 최소 권한, 보존 정책 적용

서비스 계정은 로그인 셸이 없는 전용 계정으로 만든다. 코드, DB, 설정, 백업, TLS 개인키를 Git에 넣지 않는다. 배포를 다시 실행해도 기존 DB·설정·인증서를 덮어쓰지 않는다. 실제 경로의 생성과 권한 변경은 승인된 서버에서 수행하고, UID/GID와 stat 결과로 확인한다.

3. 설치와 DB 준비

  1. README의 검증 환경을 참고해 대상 서버의 Ubuntu·Python·SQLite 버전을 실제로 확인한다. 현재 로컬 검증 값은 Ubuntu 24.04, Python 3.12.3, SQLite 3.45.1이며 다른 조합은 별도 검증이 필요하다. Python 3.11 이상은 초기 목표다.
  2. 승인된 커밋을 /opt/roomshare/releases/<commit>에 배치한다. 커밋과 requirements.lock 해시를 기록한다. 새 릴리스의 scripts/install.sh로 런타임 venv와 보호된 환경 파일을 준비한다.
  3. DB는 앱 시작 시 초기화하지 않는다. 서비스 계정으로 명시적 deploy.sh init 또는 deploy.sh upgrade <호환_이전_릴리스>를 실행한다. 기존 DB에는 백업을 먼저 검증한다. 실제 명령·lock·전환 순서는 실행서를 따른다.

--check는 기존 DB를 읽기 전용으로 확인하며 schema: ...; integrity: ok; foreign keys: ok가 나와야 한다. 모든 명령의 종료 코드도 기록한다. 기존 DB에 새 마이그레이션을 적용하기 전에는 호환성과 검증된 백업을 확인한다. 다운그레이드 명령은 제공되지 않는다.

4. 운영 설정과 앱 서비스

서비스가 읽는 환경 파일에는 최소한 아래 값을 넣는다. ROOMSHARE_PUBLIC_HOST와 ROOMSHARE_ADMIN_HOST는 스킴·포트·경로가 없는 서로 다른 실제 호스트명이어야 한다. 상대 DB 경로는 저장소 루트 기준으로 해석되므로 운영에서는 절대 경로를 쓴다. 선택적 저장소 .env보다 프로세스 환경 변수가 우선한다.

ROOMSHARE_DB_PATH=/var/lib/roomshare/roomshare.db
ROOMSHARE_TIMEZONE=Asia/Seoul
ROOMSHARE_PUBLIC_HOST=<사용자_호스트명>
ROOMSHARE_ADMIN_HOST=<관리자_호스트명>
ROOMSHARE_BOOKING_HORIZON_DAYS=<승인된_기간>
ROOMSHARE_ADMIN_ACCESS=deny
ROOMSHARE_MAX_BODY_BYTES=16384
ROOMSHARE_RATE_LIMIT_REQUESTS=120
ROOMSHARE_RATE_LIMIT_WINDOW_SECONDS=60

마지막 세 제한값은 승인 전 임시값이다. 초기에는 관리자 접근을 deny로 유지한다. mTLS 프록시 검증이 끝난 후 ROOMSHARE_ADMIN_ACCESS=proxy_mtls로 바꾸고, CSPRNG로 생성한 32바이트 이상의 URL-safe 비밀(ROOMSHARE_ADMIN_PROXY_SECRET, 43~128자)을 보호된 앱 환경 파일과 Nginx 설정에 같은 값으로 제공한다. 비밀을 터미널 기록·로그·브라우저·저장소에 남기지 않는다. 앱과 프록시의 비밀은 함께 회전한다. CSRF 비밀은 앱 시작 시 메모리에서 생성되므로 별도 파일이 필요 없다.

실제 systemd unit과 timer를 기준으로 systemd-analyze verify 후 승인된 전용 스테이징에서 기동한다. current는 검증된 릴리스에 대한 symlink다.

단일 worker가 필수다. 앱의 요청 빈도 카운터와 관리자 CSRF 키가 프로세스 메모리에 있고, 관리자 guard는 실제 loopback peer를 검사한다. --no-proxy-headers를 제거하거나 백엔드를 외부 인터페이스에 바인딩하면 신뢰 경계가 바뀐다. 앱 포트에 대한 외부 연결은 OCI 보안 규칙과 OS 방화벽에서도 차단하고 외부 클라이언트에서 확인한다. 서비스 시작 후 systemctl status, journalctl(비밀 마스킹), curl --fail http://127.0.0.1:8000/healthz로 상태를 확인한다.

5. Nginx와 인증서

Nginx 템플릿을 격리된 스테이징의 DNS·서버 키·관리 CA/CRL에 맞춘다. 아래 사항과 nginx -t·TLS/인증서 행렬을 실제 환경마다 확인한다.

  1. 443에서 두 호스트의 유효한 서버 TLS 인증서를 제공하고, 알 수 없는 SNI/Host는 기본 가상 호스트에서 거부한다. 80은 승인된 인증서 검증·HTTPS 이동 용도로만 연다. Host와 SNI가 서로 다를 때도 관리자 기능에 도달하지 못하게 한다.
  2. 사용자 호스트의 /admin, /admin/ 및 /api/admin, /api/admin/ 하위 경로를 프록시 전에 차단한다. 사용자 호스트는 관리자 검증 헤더를 upstream에 전달하지 않는다.
  3. 관리자 호스트에서는 신뢰 CA의 유효한 클라이언트 인증서가 필수다. 인증서가 없거나 다른 CA에서 발급됐거나 만료되었으면 접근을 거부한다. 인증서 폐기·갱신 절차와 CA/개인키 파일 권한을 운영자가 관리한다.
  4. 관리자 인증 성공 요청에만 Nginx가 단일 Host: <관리자 호스트>, X-RoomShare-Admin-Verified: SUCCESS, X-RoomShare-Proxy-Secret: <보호된 비밀>을 upstream에 새로 설정한다. 클라이언트가 보낸 같은 이름의 헤더는 사용하지 않는다. Forwarded, X-Forwarded-*, X-Real-IP 등 외부 전달 헤더도 제거하거나 신뢰할 수 있는 값으로 덮어쓴다. 앱은 전달 IP 헤더를 인증에 사용하지 않는다.
  5. 프록시의 본문 크기·연결 시간·빈도 제한을 설정하고 초과 시 413/429 결과를 실제 확인한다. 앱 자체의 본문/빈도 제한과 합쳐서 검증한다. 예약·관리자 응답과 오류 응답은 Cache-Control: no-store를 유지한다.
  6. Nginx 접근 로그에는 raw query/전체 URI·요청 본문·인증 헤더·취소 토큰·CSRF 토큰·프록시 비밀을 기록하지 않는다. 앱은 Uvicorn 접근 로그를 끈다. 관리자 호스트의 캐시·프록시 로그·오류 로그도 합성 데이터로 점검한다.

관리자 페이지는 관리자 호스트의 /admin으로 직접 연다. 변경 요청은 브라우저가 보낸 정확한 Origin: https://<관리자 호스트>와 발급된 CSRF 토큰을 요구한다. 테스트 코드의 인증 컨텍스트 주입은 실제 mTLS 검증 증거가 아니다. 자세한 앱 계약은 DEPLOYMENT의 RS-006/007 절을 따른다.

6. 백업과 복원

SQLite는 WAL 모드다. 실행 중인 DB 파일이나 -wal 파일만 단순 복사하지 않는다. snapshot.py의 backup과 일일 systemd timer를 사용한다.

백업 절차는 임시 파일에 일관된 스냅샷 생성 → 무결성·외래키·마이그레이션 버전 검사 → 권한 확인 → 최종 이름으로 이동 → 별도 위치 보관 순서로 설계한다. 생성 실패·검사 실패는 0이 아닌 종료 코드로 기록하고 정상 백업으로 취급하지 않는다. 백업 보존 기간은 운영자가 정하며 이력 보관 임시값 90일과 별개다. 최신 검증 백업을 보존하고, 보관 위치의 접근 권한과 디스크 여유를 정기적으로 확인한다.

restore는 새 사설 디렉터리에만 복원한다. scripts/migrate.py --db-path <복원_DB> --check 및 실제 예약·차단·설정 조회로 검증한다. 운영 전환은 명시적 승인 후 서비스 정지, 직전 백업, 원래 DB/WAL/SHM 보존, 새 DB 경로 선택, 재시작·기능 확인 순이다. 손상 백업이나 기존 목적지에는 진행하지 않는다.

7. 배포 전환·검증·되돌리기

  1. 릴리스 커밋, requirements.lock, DB 스키마 버전, 이전 릴리스와의 DB 호환성을 기록한다. 승인된 스테이징에서 전체 python -m pytest -q와 RS-008/009의 관련 검증을 수행한다.
  2. 배포 직전 검증된 백업을 확보한다. 새 코드·venv를 준비하고 마이그레이션의 영향과 중단 시간을 확인한다. 서비스 전환 실패 시 원래 릴리스로 되돌릴 수 있도록 이전 코드와 호환 DB 스냅샷을 보존한다.
  3. Nginx 설정 검사 후 승인된 서비스 전환을 수행한다. 실제 nginx -t·서비스 재시작·reload 명령, 종료 코드, 시각, 실행자를 기록한다. 오류가 나면 자동 재시도나 무조건 재제출 대신 현재 DB·프로세스 상태부터 확인한다.
  4. 아래 시험을 로컬 스테이징과 OCI에서 각각 기록한다. 실제 기기 Safari/Chrome 시험은 브라우저 자동화와 별개다.
검증 기대 결과 관련 케이스
사용자 HTTPS, 관리자 경로, 미등록 Host/SNI 공개 기능 정상, 관리자 및 미등록 호스트 차단 TC-008-04/07
관리자 인증서 없음·오류 CA·만료·유효 유효 인증서만 관리자 접근 TC-008-05
내부 헤더·Forwarded·중복 헤더 위조, 직접 백엔드 접속 권한 획득 불가, 외부 백엔드 차단 TC-008-06/08
본문/빈도 초과와 응답 헤더 제한 동작, 민감 응답 no-store TC-008-09

실패 시 트래픽 노출을 멈추고 원인을 기록한다. 이전 코드가 현재 DB 스키마와 호환되면 이전 릴리스로 되돌린다. 호환되지 않으면 보존한 호환 DB 스냅샷을 격리 검증한 뒤 승인된 복원 절차를 따른다. 데이터 손실 가능성이 있으면 임의 복원하지 않고 운영자에게 알린다.

8. 완료 기록

RS-008의 케이스별 실제 명령·종료 코드·결과는 qa/reports/RS-008.md, RS-009의 통합·릴리스 결과는 qa/reports/RS-009.md에 기록한다. 미실행·skip·환경 부족을 PASS로 바꾸지 않는다. 실제 OCI 접근이 없으면 OCI 검증은 NOT RUN으로 유지한다. 필수 보안 경계, 백업 복원, 실기기, 정책 승인 중 하나라도 미완료면 공개 릴리스는 NO-GO다.
