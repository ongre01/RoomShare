## 구현 범위 및 세부 작업
1. 관리자 UI/API 공통 guard 구현. 기본 deny. 관리자 호스트와 신뢰된 Nginx 접근 신호 모두 필요. Host/Forwarded/내부 헤더를 클라이언트가 임의 설정하는 경우를 고려한다. 실제 신뢰 경계는 RS-008의 loopback/Unix socket 제한 및 Nginx 헤더 덮어쓰기로 완성된다. 앱 단독 테스트와 프록시 통합 테스트를 구분한다. 테스트에서만 의존성 주입으로 인증 상태 모사; 운영 우회 설정 금지.
2. 관리자 변경 POST/PATCH/DELETE에 정확한 HTTPS Origin(설정된 관리자 호스트)과 CSRF 토큰 검증을 요구한다. 토큰 발급/전송 방식(예: 서버가 서명한 토큰, 요청 헤더), 만료 및 비밀 설정을 문서화한다. 부재/오류/타 호스트 거부. 로그인 화면 추가 금지.
3. GET/POST /api/admin/reservations, PATCH/DELETE /api/admin/reservations/{id} 구현. 조회는 월 범위 및 예약 상태에 맞춰 반환하고 토큰/해시를 제외한다. 관리자 생성은 공개 생성 서비스 재사용. 수정은 기존 점유 해제/새 점유 등록/정보 변경/이력을 한 트랜잭션으로 처리하고 충돌 시 기존 예약 완전 유지. 취소는 상태/로그 보존 및 점유 제거. 과거 날짜 수정/취소 권한은 문서에 확정되지 않았으므로 안전한 임시 정책을 명시하고 무단 과거 변경 방지(제안: 과거 포함 예약의 날짜 변경/취소 금지; 메모 수정 허용 여부 별도 결정).
4. POST /api/admin/blocked-dates, DELETE /api/admin/blocked-dates/{date} 구현. 같은 날짜 PK 사용. 여러 날짜 일괄 등록은 원자적이며 예약과 충돌하면 409. 메모 길이 검증. 해제는 BLOCKED 행만 삭제하고 RESERVED 행은 삭제하지 않는다. 로그와 같은 트랜잭션.
5. GET /api/admin/logs는 안정적인 정렬/페이지네이션, 상한 있는 page size; 토큰/해시 제외. GET/PATCH /api/admin/settings는 booking_horizon_days 검증/저장/로그. 기간 변경은 기존 예약/차단을 삭제하지 않는다. 기간 상한 및 페이지네이션 기본값은 제안으로 문서화한다.
6. 관리자 응답 no-store 적용 제안, 오류 표준화. 모든 관리자 경로와 향후 UI 진입점에 guard 적용. RS-004의 공통 schema/오류 파일과 충돌하지 않게 협의한다.

## 구현 심화 지침 (v2, 제안)
1. 관리자 권한 경계를 먼저 계약화한다. 외부 클라이언트가 보낸 헤더는 신뢰하지 않으며 Nginx가 인증 후 전달하는 신호와 앱의 직접 접근 차단을 함께 사용한다. 테스트 주입 컨텍스트는 production configuration으로 전환할 수 없어야 한다. localhost에서 신호를 보낼 수 있다는 사실만으로 외부 경계가 검증된 것은 아니다.
2. CSRF는 발급/만료/검증/전달 위치와 비밀 관리, Origin 정확 일치 여부를 문서화한다. 변경 API 모두 공통 guard 적용 후 요청을 처리한다. GET은 상태 변경 금지. 공개 경로의 권한과 혼용 금지.
3. 수정은 자기 날짜 제외 충돌 검사 및 전체 교체를 하나의 거래로 수행한다. 날짜 변경 없는 정보 수정도 기존 날짜를 잃지 않아야 한다. 관리자 생성 토큰 처리 및 과거일 정책, PATCH 필드 생략 의미, 월 조회에서 예약 전체 날짜 반환을 API 계약으로 명시한다.
4. 설정은 현재 예약 가능 기간에만 영향을 주며 기존 점유를 삭제하지 않는다. 로그 정렬은 timestamp와 고유 ID 등 안정 tie-breaker를 사용한다. 로그 보존 자동 삭제는 정책 승인 전 별도 확장하지 않는다.
5. RS-004와 공통 schemas/errors/middleware 변경 충돌을 사전에 조율한다. 취소 로직 공통화가 필요하더라도 권한별 정책을 섞지 않는다.
