# RS-003 실행 프롬프트

당신은 RoomShare 프로젝트의 소프트웨어 개발 Agent다. 현재 저장소에서 **RS-003 — 예약 엔진 및 충돌 방지**만 실제 구현하라. 단순 설계 제안이나 코드 예시만 작성하지 말고, 필요한 파일을 수정하고 테스트를 실행하라.

## 먼저 읽을 파일
`AGENTS.md`, `README.md`, `docs/REQUIREMENTS.md`, `docs/DECISIONS.md`, `docs/DESIGN.md`, `docs/API.md`, `docs/DEPLOYMENT.md`, `tickets/INDEX.md`, `tickets/RS-003.md`, `prompts/COMMON.md`.
공통 작업 지침을 적용하며 선행 티켓(RS-002)의 실제 완료 및 산출물을 검증하라. 사용자 변경 보존 및 테스트 전용 DB 사용. 운영 서버 변경/push/merge 금지.

## 이번 작업의 목표
HTTP와 분리된 재사용 예약 서비스로 날짜 정책, 달력 조회 및 원자적 예약 생성 구현.

## 수행할 작업
1. 테스트 가능한 clock을 도입한다. 날짜는 정확한 YYYY-MM-DD 및 실제 날짜로 검증. 오늘은 KST 기준. 오늘 포함 N일은 [today, today + N - 1일]로 정의한다(임시값 90). 이름 1~40자(공백만 금지), 메모 최대 200자, 빈 날짜 배열/중복 날짜/과거/범위 초과 거부. 선택 수 제한은 현 예약 기간으로 제한한다.
2. 서비스 계층에서 월별 달력 조회를 제공한다. YYYY-MM 및 월말/윤년 검증, dates/today/min_date/max_date 반환. 과거는 PAST 우선, 현재/미래 점유는 RESERVED/BLOCKED, 그 외 AVAILABLE. 기간 밖 미래는 API의 max_date로 선택 불가 처리(새 enum 임의 추가 금지).
3. 예약 ID UUID, 암호학적 난수 32바이트 이상 URL-safe 토큰 생성, SHA-256 해시만 저장. 생성 결과에서만 평문 반환. UTC 타임스탬프 기록.
4. BEGIN IMMEDIATE 안에서 현재 설정/날짜/충돌 검증, 예약 행, 모든 점유 행, 생성 이력을 한 번에 삽입한다. 날짜 PK 충돌은 도메인 충돌 오류로 변환하고 충돌 날짜만 제공. DB busy/locked는 별도 일시 오류. 예상치 못한 DB 오류를 모두 날짜 충돌로 처리하지 않는다.
5. 관리자 서비스에서 재사용할 날짜 검증/점유/로그 helper의 책임을 명시한다. 서비스에서 HTTP 상태 코드를 직접 생성하지 않는다. 취소/수정 API는 후속 티켓 범위.

## 변경 범위
app/services/reservations.py, app/services/calendar.py, app/services/date_policy.py, app/services/errors.py, app/services/tokens.py, tests/test_reservation_service.py, tests/test_concurrency.py
파일명은 제안이며 실제 저장소 구조에 맞추되 범위를 확대하지 마라.

## 테스트 요구
- 날짜 1개/복수/비연속, 월 경계를 넘는 예약 성공.
- 동일 날짜 두 요청을 독립 SQLite 연결과 동시 시작 barrier로 경쟁시켜 성공 정확히 1건, 다른 요청 충돌, DB 예약/점유/로그에 유령 행 없음.
- 복수 날짜 중 한 날짜 예약 또는 차단 충돌 시 신규 점유 및 예약/로그 전체 롤백.
- 빈/중복/잘못된 날짜, 2월 29일, 12월→1월, 오늘 포함 90일 마지막 날과 다음 날, KST 자정 전후, 공백 이름/문자수 경계.
- busy timeout 시 명확한 일시 오류, 임의 DB 오류가 충돌로 오분류되지 않음.
- DB와 로그에 평문 토큰 없음; 달력에 이름/메모/예약 ID 없음.

## 심화 실행 절차 (v2)
반드시 `docs/TEST_PLAN.md`, `qa/specs/RS-003.md`, `qa/REPORT_TEMPLATE.md`, `qa/TRACEABILITY.md`를 추가로 읽어라. 다음 지침은 기존 티켓의 구현 범위와 함께 적용한다.

1. 공개 서비스 계약을 먼저 문서화한다. calendar(month, clock), create_reservation(name,memo,dates) 등 이름은 제안이며 결과/도메인 예외/트랜잭션 책임을 확정한다. 입력의 날짜 파싱과 정책 적용, 상태 조회를 HTTP 계층과 분리한다.
2. 생성 흐름: 입력 정규화 및 구문 검증 → BEGIN IMMEDIATE → 현재 DB 설정 및 clock 확인 → 전체 날짜 정책/충돌 검사 → 예약/점유/로그 삽입 → commit → 응답. 오류 시 rollback 후 충돌/일시 장애/예상외 오류 분류. 커밋 전에 토큰을 외부에 반환하지 않는다.
3. 부분 실패 및 경쟁 테스트는 mock만으로 대체하지 않는다. 각 작업이 별도 DB 연결을 열고 barrier에 timeout을 둔다. join 실패도 테스트 실패로 처리한다. 충분한 lock timeout의 정상 경쟁과 의도적 busy timeout을 분리한다.
4. 날짜 정책 테스트는 고정 UTC clock을 KST로 변환하며 API/UI가 브라우저 timezone에 의존하지 않도록 계약을 전달한다. 해시만 DB에 남는지 실제 행과 로그를 검사한다.

### 구현 및 테스트 수행 순서
1. 선행 산출물과 현재 코드를 확인하고 이번 티켓의 파일/인터페이스/테스트 계획을 작성한다. 아직 구현되지 않은 후속 기능은 범위에 넣지 않는다.
2. 다음 명세를 기준으로 가능한 자동화 테스트를 작성한다. 미구현 기능의 실패 또는 기존 기준선을 실제 실행하고, 테스트의 실패 이유를 기록한다. 존재하지 않는 테스트를 실행했다고 주장하지 않는다.
3. 기능을 구현하고 정상/오류/경계 케이스를 반복 실행한다. 실제 SQLite가 필요한 테스트에 mock DB를 쓰지 않는다. 수동 케이스는 실제 환경에서만 PASS 처리한다.
4. 명세의 기대 결과를 상태·응답·DB/로그 등 해당 관찰 지점에서 직접 검증한다. 관련 TC ID를 테스트명, 파라미터 ID 또는 보고서에 연결한다.
5. 아래 목록 전체와 상세 명세의 사전 조건·절차를 확인한다. 케이스를 임의 삭제하거나 skip으로 통과시키지 않는다.
- `TC-003-01` [unit/local] 예약 날짜 경계 → 12/01~02/28만 허용; 나머지 거부
- `TC-003-02` [unit/local] KST 자정 → KST 11/30 및 12/01로 변경; 시스템 TZ 무관
- `TC-003-03` [unit/local] 정확한 날짜 파싱 → 윤년 유효 날짜만 허용, 비정규 형식/실재하지 않는 날짜 거부
- `TC-003-04` [unit/local] 월 길이 및 연도 경계 → 29/28/31/31개 날짜; 잘못된 월 오류
- `TC-003-05` [unit/local] 입력 제한 → 계약 내 값만 허용; 잘못된 입력 DB 변경 없음
- `TC-003-06` [integration/local] 복수 월 비연속 예약 → 예약 1, 점유 3, 생성 로그 1; 정렬된 날짜 및 UUID 반환
- `TC-003-07` [integration/local] 달력 상태 및 개인정보 → PAST 우선, RESERVED/BLOCKED/AVAILABLE 구분; 이름/메모/ID 없음
- `TC-003-08` [concurrency/local] 같은 날짜 2중 경쟁 → 매회 성공 1/충돌 1, 예약/점유/생성 로그 각 1; deadlock 없음
- `TC-003-09` [concurrency/local] 부분 중복 경쟁 → 정확히 1건 전체 성공, 패자 전용 날짜 미점유, 유령 예약/로그 없음
- `TC-003-10` [integration/local] 예약/차단 충돌 롤백 → 409에 대응하는 도메인 충돌; DB 스냅샷 불변
- `TC-003-11` [integration/local] 중간 예외 롤백 → 예약/점유/이력 모두 롤백, 예외 숨김 없음
- `TC-003-12` [integration/local] busy와 예상외 오류 분류 → busy는 일시 오류, 다른 SQL 오류는 충돌로 오분류하지 않음
- `TC-003-13` [security/local] 토큰 생성/저장 → 서로 다른 난수 토큰, DB는 해시만, 로그/달력 평문 없음
- `TC-003-14` [integration/local] 기간 설정 변경 반영 → 현재 설정을 거래 내 읽음; 기존 점유 보존
6. 대상 테스트 및 전체 pytest를 실행하고 결과/종료 코드/수집 건수/실패·skip을 기록한다. 브라우저, Nginx, OCI 등 별도 테스트는 실제 명령 및 환경 증거를 남긴다.
7. 자기 변경에 대한 코드 리뷰를 수행한다. 요구사항 및 API 계약, 오류 경계, 데이터 무결성, 보안, 불필요한 의존성, 테스트 독립성, 변경 범위를 확인하고 발견한 결함은 회귀 케이스와 함께 수정한다.
8. `qa/REPORT_TEMPLATE.md`를 사용해 `qa/reports/RS-003.md`를 작성하고 `qa/TEST_CASES.csv`에서 자신의 케이스 상태를 갱신한다. `tickets/RS-003.md` 및 INDEX의 완료 증거도 기록한다. 실행되지 않은 외부 환경 검증은 NOT RUN/BLOCKED로 남긴다.
9. 기존 완료 조건과 TEST_PLAN의 품질 게이트를 모두 충족할 때만 DONE으로 판단한다. 실제 Git 권한이 있을 때만 자기 변경을 커밋하고 push/merge/후속 티켓 착수는 하지 않는다.
