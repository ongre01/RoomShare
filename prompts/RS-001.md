# RS-001 실행 프롬프트

당신은 RoomShare 프로젝트의 소프트웨어 개발 Agent다. 현재 저장소에서 **RS-001 — 프로젝트 초기화**만 실제 구현하라. 단순 설계 제안이나 코드 예시만 작성하지 말고, 필요한 파일을 수정하고 테스트를 실행하라.

## 먼저 읽을 파일
`AGENTS.md`, `README.md`, `docs/REQUIREMENTS.md`, `docs/DECISIONS.md`, `docs/DESIGN.md`, `docs/API.md`, `docs/DEPLOYMENT.md`, `tickets/INDEX.md`, `tickets/RS-001.md`, `prompts/COMMON.md`.
공통 작업 지침을 적용하며 선행 티켓(없음)의 실제 완료 및 산출물을 검증하라. 사용자 변경 보존 및 테스트 전용 DB 사용. 운영 서버 변경/push/merge 금지.

## 이번 작업의 목표
실행 가능한 최소 FastAPI 앱과 재현 가능한 로컬 개발 환경 구축. 예약 기능은 구현하지 않는다.

## 수행할 작업
1. 앱 팩토리 `create_app`과 ASGI 진입점 구현. 설정을 테스트에서 주입할 수 있게 분리한다. import만으로 운영 DB를 생성하지 않는다.
2. .env.example의 DB_PATH, TIMEZONE, PUBLIC_HOST, ADMIN_HOST, BOOKING_HORIZON_DAYS, ADMIN_ACCESS를 읽는다. 환경 변수와 .env 로딩 방식/우선순위를 문서화한다. timezone은 Asia/Seoul, 기본 관리자 접근은 deny, 두 호스트는 서로 달라야 한다. 기간은 양의 정수이며 빈 경로/잘못된 호스트/지원하지 않는 관리자 모드 등은 명확한 시작 오류로 처리한다.
3. Jinja2 템플릿/정적 파일 경로를 소스 위치 기준으로 해석하고 기본 레이아웃에 모바일 viewport를 포함한다. GET /healthz는 최소 JSON 응답만 반환한다. 공개 `/`는 후속 티켓이 구현할 자리만 제공한다.
4. Python 3.11 이상 초기 목표에 맞춰 실제 `python --version` 기록, venv, 런타임/개발 lock 파일 생성 방식과 설치 명령을 README에 작성한다. lock 버전을 추측하지 말고 실제 설치·호환성 검증한다.
5. 테스트 fixture에서 임시 디렉터리/설정 주입을 가능하게 한다. 외부 인터페이스 대신 로컬 기본 바인딩 사용. 실제 관리자 bypass를 개발 편의로 만들지 않는다.

## 변경 범위
app/main.py, app/config.py, app/templates/base.html, app/static/, tests/conftest.py, tests/test_health.py, requirements*.in, requirements*.lock, README.md, .env.example
파일명은 제안이며 실제 저장소 구조에 맞추되 범위를 확대하지 마라.

## 테스트 요구
- 정상 설정에서 앱 생성 및 GET /healthz 200, 응답에 경로/환경 변수/버전/비밀 없음.
- 잘못된 기간(0, 음수, 문자), 동일 호스트, 잘못된 timezone 및 관리자 모드의 시작 실패.
- 다른 작업 디렉터리에서도 템플릿/정적 파일 경로 정상.
- 깨끗한 venv에서 lock 설치 후 README 명령으로 실행, 로컬 HTTP 확인, pytest smoke 및 전체 테스트.

## 심화 실행 절차 (v2)
반드시 `docs/TEST_PLAN.md`, `qa/specs/RS-001.md`, `qa/REPORT_TEMPLATE.md`, `qa/TRACEABILITY.md`를 추가로 읽어라. 다음 지침은 기존 티켓의 구현 범위와 함께 적용한다.

1. 먼저 저장소 실제 상태를 확인하고 설정 객체의 공개 필드/환경 변수 매핑 및 우선순위를 명시한다. `create_app(settings=...)` 형태의 주입 가능한 계약을 제안하되 실제 이름은 문서에 확정한다. 모듈 로딩, 앱 생성, lifespan의 부작용을 각각 구분한다.
2. 가상환경/lock 생성·설치 절차를 분리한다. 현재 환경 Python 버전과 SQLite 버전을 기록하고 실제 설치한 버전으로 lock을 만든다. 테스트용 도구와 운영 의존성 분리; 설치 불가 시 버전을 지어내지 않는다.
3. `tests/conftest.py`에 임시 설정 fixture, 이후 DB fixture 확장점과 앱 client fixture를 마련한다. RS-002부터 마이그레이션된 DB를 연결한다. 아직 없는 기능의 가짜 구현으로 테스트를 통과시키지 않는다.
4. healthz는 최소 JSON(예: `{ "status": "ok" }`, 정확한 형식 문서화)을 반환하며 내부 상태를 노출하지 않는다. 초기 관리자 미구현 경로와 RS-006 이후 권한 guard의 검증 범위를 구분한다.

### 구현 및 테스트 수행 순서
1. 선행 산출물과 현재 코드를 확인하고 이번 티켓의 파일/인터페이스/테스트 계획을 작성한다. 아직 구현되지 않은 후속 기능은 범위에 넣지 않는다.
2. 다음 명세를 기준으로 가능한 자동화 테스트를 작성한다. 미구현 기능의 실패 또는 기존 기준선을 실제 실행하고, 테스트의 실패 이유를 기록한다. 존재하지 않는 테스트를 실행했다고 주장하지 않는다.
3. 기능을 구현하고 정상/오류/경계 케이스를 반복 실행한다. 실제 SQLite가 필요한 테스트에 mock DB를 쓰지 않는다. 수동 케이스는 실제 환경에서만 PASS 처리한다.
4. 명세의 기대 결과를 상태·응답·DB/로그 등 해당 관찰 지점에서 직접 검증한다. 관련 TC ID를 테스트명, 파라미터 ID 또는 보고서에 연결한다.
5. 아래 목록 전체와 상세 명세의 사전 조건·절차를 확인한다. 케이스를 임의 삭제하거나 skip으로 통과시키지 않는다.
- `TC-001-01` [unit/local] 정상 설정 → 정규화된 값 일치, 관리자 기본 deny
- `TC-001-02` [unit/local] 잘못된 예약 기간 → 각 오류를 명시적으로 거부하고 서비스 시작하지 않음
- `TC-001-03` [unit/local] 호스트 및 접근 모드 검증 → 유효하지 않은 설정 거부; 우회 모드 생성 없음
- `TC-001-04` [unit/local] 설정 우선순위 → 문서화된 우선순위와 기본값 일치, 다른 테스트에 오염 없음
- `TC-001-05` [unit/local] import 부작용 → DB 생성 및 외부 서비스 연결 없음
- `TC-001-06` [api/local] healthz 응답 → 200, 최소 JSON, DB 경로/비밀/버전/traceback 없음
- `TC-001-07` [api/local] 초기 관리자 경로 → 미구현 404 또는 명시적 거부, 관리 기능/정보 없음
- `TC-001-08` [integration/local] 작업 경로 독립성 → 절대 경로 하드코딩 없이 정상 렌더링; viewport 확인
- `TC-001-09` [deploy/local] 깨끗한 venv → 설치 및 시작 성공, 종료 후 프로세스 정리; 버전/명령 기록
- `TC-001-10` [integration/local] 테스트 격리 → 서로의 설정/파일/환경 변수를 공유하지 않음
6. 대상 테스트 및 전체 pytest를 실행하고 결과/종료 코드/수집 건수/실패·skip을 기록한다. 브라우저, Nginx, OCI 등 별도 테스트는 실제 명령 및 환경 증거를 남긴다.
7. 자기 변경에 대한 코드 리뷰를 수행한다. 요구사항 및 API 계약, 오류 경계, 데이터 무결성, 보안, 불필요한 의존성, 테스트 독립성, 변경 범위를 확인하고 발견한 결함은 회귀 케이스와 함께 수정한다.
8. `qa/REPORT_TEMPLATE.md`를 사용해 `qa/reports/RS-001.md`를 작성하고 `qa/TEST_CASES.csv`에서 자신의 케이스 상태를 갱신한다. `tickets/RS-001.md` 및 INDEX의 완료 증거도 기록한다. 실행되지 않은 외부 환경 검증은 NOT RUN/BLOCKED로 남긴다.
9. 기존 완료 조건과 TEST_PLAN의 품질 게이트를 모두 충족할 때만 DONE으로 판단한다. 실제 Git 권한이 있을 때만 자기 변경을 커밋하고 push/merge/후속 티켓 착수는 하지 않는다.
