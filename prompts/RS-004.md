# RS-004 실행 프롬프트

당신은 RoomShare 프로젝트의 소프트웨어 개발 Agent다. 현재 저장소에서 **RS-004 — 사용자 예약 API 및 취소**만 실제 구현하라. 단순 설계 제안이나 코드 예시만 작성하지 말고, 필요한 파일을 수정하고 테스트를 실행하라.

## 먼저 읽을 파일
`AGENTS.md`, `README.md`, `docs/REQUIREMENTS.md`, `docs/DECISIONS.md`, `docs/DESIGN.md`, `docs/API.md`, `docs/DEPLOYMENT.md`, `tickets/INDEX.md`, `tickets/RS-004.md`, `prompts/COMMON.md`.
공통 작업 지침을 적용하며 선행 티켓(RS-003)의 실제 완료 및 산출물을 검증하라. 사용자 변경 보존 및 테스트 전용 DB 사용. 운영 서버 변경/push/merge 금지.

## 이번 작업의 목표
공개 API 계약을 구현하고 로그인 없이 본인 예약 전체 취소를 제공한다.

## 수행할 작업
1. GET /api/calendar?month=YYYY-MM, POST /api/reservations, POST /api/reservations/cancel을 구현한다. 요청/응답 모델을 명시하고 알 수 없는 필드, 타입 오류, 잘못된 JSON, 정책 위반을 처리한다. 201/400 또는 422/404/409/429/503은 API.md에 맞춰 일관된 오류 JSON으로 변환한다.
2. 공개 생성 응답은 id, dates, status, cancel_token만 포함하고 달력은 날짜와 상태 및 범위만 노출한다. 생성·취소 응답(오류 포함)은 Cache-Control: no-store. 토큰은 URL/query가 아니라 요청 body로만 받는다.
3. 취소는 트랜잭션 안에서 ID 조회, 해시 비교(상수 시간 비교), 상태/정책 검사, 점유 삭제, CANCELLED/UTC cancelled_at 및 이력 기록. 사용자 취소는 모든 점유 날짜가 오늘보다 미래일 때만 허용한다(임시 정책). 잘못된 ID와 토큰은 동일한 외부 오류. 반복 취소 처리 방식을 API.md에 명시하고 점유/로그 중복 변경 금지.
4. 공개 CORS 기본 비허용. 입력 크기 제한과 요청 빈도 제한을 구현 또는 배포와의 책임 분담을 명확히 한다. 개발/테스트 설정을 제외한 임의 우회 금지. 제한 숫자는 제안으로 기록하고 실제 운영 조정 가능하게 한다. IP 식별은 신뢰된 프록시에서만 가져온다. body/토큰 로깅 금지.
5. 테스트에서 실제 SQLite를 사용하여 API와 서비스의 통합 동작을 검증. 오류 응답에 traceback, SQL, 개인 정보가 없어야 한다.

## 변경 범위
app/routers/public.py, app/schemas.py, app/services/cancellation.py, app/middleware.py, tests/test_public_api.py, tests/test_cancellation.py, docs/API.md
파일명은 제안이며 실제 저장소 구조에 맞추되 범위를 확대하지 마라.

## 테스트 요구
- 달력 200, 생성 201, 동일 날짜 409 및 dates 응답, 정상 취소 후 동일 날짜 다시 예약 가능.
- 잘못된 ID/토큰의 동일 상태/오류, 당일/과거 포함 예약 취소 거부 및 기존 점유 유지.
- 취소 중 오류 발생 시 상태/점유/로그 rollback, 반복 취소 정책 검증.
- 생성/취소 성공·실패 no-store, 달력 및 오류에 개인정보/토큰 미노출.
- 잘못된 JSON/타입/초과 문자열/큰 요청, 요청 빈도 제한 및 CORS 미허용.
- 서비스 경합 오류의 503 매핑.

## 심화 실행 절차 (v2)
반드시 `docs/TEST_PLAN.md`, `qa/specs/RS-004.md`, `qa/REPORT_TEMPLATE.md`, `qa/TRACEABILITY.md`를 추가로 읽어라. 다음 지침은 기존 티켓의 구현 범위와 함께 적용한다.

1. API.md의 3개 경로를 request/response schema로 고정한다. Pydantic 검증 오류에서 raw input 등 민감값을 제거하고 오류 코드 표를 작성한다. 400/422 중 구체적 매핑, 반복 취소와 잘못된 ID/토큰의 공통 응답을 구현 전에 명시한다.
2. 취소의 조회/해시 비교/상태·날짜 정책 검증/점유 삭제/상태 갱신/로그 삽입은 동일 트랜잭션 안에서 수행한다. 인증 실패, 정책 실패, 충돌 및 busy를 구분하되 ID 존재 여부를 누설하지 않는다.
3. 요청 제한의 앱/프록시 책임과 설정값을 기록한다. 프록시 제한이면 RS-008에 실제 검증을 연결하고 앱 테스트만으로 통과했다고 주장하지 않는다. CORS 응답은 브라우저 접근 정책이지 직접 요청의 인증 수단이 아니다.
4. 예약 생성의 응답 손실 시 성공 여부가 불명확할 수 있음을 사용자 UI에 인계한다. 새로운 idempotency 계약을 임의 추가하지 않고 자동 재시도하지 않는다. 토큰은 본인 생성 응답에서만 예외적으로 반환한다.

### 구현 및 테스트 수행 순서
1. 선행 산출물과 현재 코드를 확인하고 이번 티켓의 파일/인터페이스/테스트 계획을 작성한다. 아직 구현되지 않은 후속 기능은 범위에 넣지 않는다.
2. 다음 명세를 기준으로 가능한 자동화 테스트를 작성한다. 미구현 기능의 실패 또는 기존 기준선을 실제 실행하고, 테스트의 실패 이유를 기록한다. 존재하지 않는 테스트를 실행했다고 주장하지 않는다.
3. 기능을 구현하고 정상/오류/경계 케이스를 반복 실행한다. 실제 SQLite가 필요한 테스트에 mock DB를 쓰지 않는다. 수동 케이스는 실제 환경에서만 PASS 처리한다.
4. 명세의 기대 결과를 상태·응답·DB/로그 등 해당 관찰 지점에서 직접 검증한다. 관련 TC ID를 테스트명, 파라미터 ID 또는 보고서에 연결한다.
5. 아래 목록 전체와 상세 명세의 사전 조건·절차를 확인한다. 케이스를 임의 삭제하거나 skip으로 통과시키지 않는다.
- `TC-004-01` [api/local] 달력 계약 → 200, dates/today/min_date/max_date, 허용 enum, 개인정보 없음
- `TC-004-02` [api/local] 예약 생성 응답 → 201, id/dates/status/cancel_token만, no-store; DB 점유/로그 확인
- `TC-004-03` [api/local] 날짜 충돌 → 409, DATE_CONFLICT 및 충돌 dates, 기존 DB 불변
- `TC-004-04` [api/local] 잘못된 payload → 문서화된 400/422 오류, 민감 값/traceback 미노출, 변경 없음
- `TC-004-05` [api/local] 취소와 재예약 → CANCELLED, cancelled_at UTC, 점유 제거, 로그 1건; 재예약 201
- `TC-004-06` [security/local] 잘못된 토큰과 ID → 동일 외부 상태/코드/메시지, DB 불변, 존재 여부 누출 없음
- `TC-004-07` [api/local] 당일 포함 취소 제한 → 문서화된 정책 오류, 모든 점유/상태 유지
- `TC-004-08` [integration/local] 취소 중 실패 → CONFIRMED 및 전체 점유 유지, 취소 로그 없음
- `TC-004-09` [api/local] 반복 및 동시 취소 → 문서화된 반복 정책, 실제 상태 변경과 취소 로그 최대 1회
- `TC-004-10` [security/local] 민감 응답 및 로그 → 생성 성공의 본인 토큰 외 평문 노출 없음, 생성/취소 no-store
- `TC-004-11` [security/local] CORS → 타 Origin 허용 헤더 없음; CORS 자체를 인증으로 간주하지 않음
- `TC-004-12` [api/local] 요청 제한 → 구현 책임 계층에서 초과 거부(크기 코드 합의/빈도 429), 위조 IP로 우회 불가; 프록시 검증은 RS-008
- `TC-004-13` [api/local] 잠금 오류 매핑 → 503, 일반화된 메시지, 부분 쓰기 없음
- `TC-004-14` [security/local] SQL 삽입 문자열 → 문자열 데이터로만 처리, 테이블 유지
6. 대상 테스트 및 전체 pytest를 실행하고 결과/종료 코드/수집 건수/실패·skip을 기록한다. 브라우저, Nginx, OCI 등 별도 테스트는 실제 명령 및 환경 증거를 남긴다.
7. 자기 변경에 대한 코드 리뷰를 수행한다. 요구사항 및 API 계약, 오류 경계, 데이터 무결성, 보안, 불필요한 의존성, 테스트 독립성, 변경 범위를 확인하고 발견한 결함은 회귀 케이스와 함께 수정한다.
8. `qa/REPORT_TEMPLATE.md`를 사용해 `qa/reports/RS-004.md`를 작성하고 `qa/TEST_CASES.csv`에서 자신의 케이스 상태를 갱신한다. `tickets/RS-004.md` 및 INDEX의 완료 증거도 기록한다. 실행되지 않은 외부 환경 검증은 NOT RUN/BLOCKED로 남긴다.
9. 기존 완료 조건과 TEST_PLAN의 품질 게이트를 모두 충족할 때만 DONE으로 판단한다. 실제 Git 권한이 있을 때만 자기 변경을 커밋하고 push/merge/후속 티켓 착수는 하지 않는다.
