# RS-010 실행 프롬프트

당신은 RoomShare 프로젝트의 소프트웨어 개발 Agent다. 현재 저장소에서 **RS-010 — PWA 홈 화면 지원**만 실제 구현하라. 단순 설계 제안이나 코드 예시만 작성하지 말고, 필요한 파일을 수정하고 테스트를 실행하라.

## 먼저 읽을 파일
`AGENTS.md`, `README.md`, `docs/REQUIREMENTS.md`, `docs/DECISIONS.md`, `docs/DESIGN.md`, `docs/API.md`, `docs/DEPLOYMENT.md`, `tickets/INDEX.md`, `tickets/RS-010.md`, `prompts/COMMON.md`.
공통 작업 지침을 적용하며 선행 티켓(RS-009)의 실제 완료 및 산출물을 검증하라. 사용자 변경 보존 및 테스트 전용 DB 사용. 운영 서버 변경/push/merge 금지.

## 이번 작업의 목표
MVP 완료 후 선택적으로 사용자 홈 화면 추가를 제공. 오프라인 예약은 지원하지 않는다.

## 수행할 작업
1. RS-009 완료와 PWA 작업 승인 여부 확인. 사용자 호스트에만 manifest, 앱 이름, start_url, scope, 로컬 아이콘 연결. 관리자 템플릿에는 등록하지 않는다.
2. Service worker는 공개 정적 파일 allowlist만 캐시하도록 제한한다. 페이지 HTML/달력 API/예약/취소/관리자/토큰/개인정보 응답, 비 GET 요청은 캐시 및 오프라인 재생 금지. 이전 cache version 정리 및 배포 시 갱신 계획.
3. 네트워크 연결이 없으면 예약/취소가 불가능하다고 명확히 표시한다. 서버 응답 없이는 성공 상태 표시 금지. background sync/자동 재전송/오프라인 예약 저장 금지.
4. 기존 공개 모바일 UI, 보안 헤더 및 no-store와 충돌하지 않도록 한다. HTTPS 테스트 환경에서 설치/업데이트 확인. iOS Safari와 Android Chrome의 실제 확인 결과를 구분한다.

## 변경 범위
app/static/manifest.webmanifest, app/static/icons/, app/static/js/sw.js 또는 공개 SW 경로, app/templates/index.html, tests/test_pwa.py, tests/manual/pwa.md
파일명은 제안이며 실제 저장소 구조에 맞추되 범위를 확대하지 마라.

## 테스트 요구
- manifest/아이콘/서비스워커 정상 경로 및 공개 호스트 scope 검증.
- 관리자/HTML/API/POST/토큰 응답 캐시 부재(Cache Storage 검사).
- 오프라인 예약/취소 실패 안내 및 재연결 후 수동 조회, 자동 제출 없음.
- cache 갱신 및 이전 정적 파일 제거, 기존 예약 흐름 회귀 테스트.
- iOS/Android 실제 홈 화면 추가 확인, 없는 장치는 NOT RUN.

## 심화 실행 절차 (v2)
반드시 `docs/TEST_PLAN.md`, `qa/specs/RS-010.md`, `qa/REPORT_TEMPLATE.md`, `qa/TRACEABILITY.md`를 추가로 읽어라. 다음 지침은 기존 티켓의 구현 범위와 함께 적용한다.

1. 사용자 호스트에만 manifest/아이콘/SW 등록한다. scope와 실제 경로를 브라우저에서 검증하고 관리자 호스트와 공유되는 경우 캐시 정책을 재검토한다. 실제 지원 차이는 설치 테스트 결과로만 기록한다.
2. 정적 리소스 GET allowlist에만 cache 전략을 적용한다. HTML 및 API 요청은 네트워크 전용이며 오프라인 때 성공 응답을 합성하지 않는다. cache 이름 prefix/version으로 다른 앱의 캐시를 삭제하지 않는다.
3. SW 갱신과 이전 리소스 제거를 검증한다. offline→online 전환은 사용자가 명시적으로 재조회/재시도하도록 하고 background sync, 자동 재전송, 예약 내용 저장을 추가하지 않는다.
4. 브라우저 지원이 없는 경우 기존 웹 기능을 그대로 사용할 수 있어야 한다. PWA 실패가 MVP 예약 동작에 영향을 주면 롤백/비활성화 방법을 제공한다.

### 구현 및 테스트 수행 순서
1. 선행 산출물과 현재 코드를 확인하고 이번 티켓의 파일/인터페이스/테스트 계획을 작성한다. 아직 구현되지 않은 후속 기능은 범위에 넣지 않는다.
2. 다음 명세를 기준으로 가능한 자동화 테스트를 작성한다. 미구현 기능의 실패 또는 기존 기준선을 실제 실행하고, 테스트의 실패 이유를 기록한다. 존재하지 않는 테스트를 실행했다고 주장하지 않는다.
3. 기능을 구현하고 정상/오류/경계 케이스를 반복 실행한다. 실제 SQLite가 필요한 테스트에 mock DB를 쓰지 않는다. 수동 케이스는 실제 환경에서만 PASS 처리한다.
4. 명세의 기대 결과를 상태·응답·DB/로그 등 해당 관찰 지점에서 직접 검증한다. 관련 TC ID를 테스트명, 파라미터 ID 또는 보고서에 연결한다.
5. 아래 목록 전체와 상세 명세의 사전 조건·절차를 확인한다. 케이스를 임의 삭제하거나 skip으로 통과시키지 않는다.
- `TC-010-01` [api/local] manifest 및 리소스 → 유효 JSON/리소스, 공개 시작 URL, 관리자 등록 없음
- `TC-010-02` [e2e/local] 정적 캐시 allowlist → 지정 정적 GET만 캐시, 동적/관리자/민감 정보 없음
- `TC-010-03` [e2e/local] 오프라인 예약/취소 → 오프라인 안내, 성공 표시/큐/백그라운드 제출 없음
- `TC-010-04` [e2e/local] 재연결 → 자동 생성/취소 요청 0건, 사용자 직접 재시도만 허용
- `TC-010-05` [e2e/local] SW 버전 갱신 → 자기 버전의 구 캐시 제거, 새 정적 리소스 제공, 다른 앱 캐시 미삭제
- `TC-010-06` [e2e/local] 민감 데이터 회귀 → 토큰/관리자/예약 API 미저장, no-store 유지
- `TC-010-07` [e2e/local] 온라인 기능 회귀 → 기존 계약과 DB 결과 일치, stale calendar 없음
- `TC-010-08` [manual/device] 홈 화면 실제 설치 → 지원 동작 및 플랫폼 차이 기록; 실제 기기 없으면 NOT RUN
6. 대상 테스트 및 전체 pytest를 실행하고 결과/종료 코드/수집 건수/실패·skip을 기록한다. 브라우저, Nginx, OCI 등 별도 테스트는 실제 명령 및 환경 증거를 남긴다.
7. 자기 변경에 대한 코드 리뷰를 수행한다. 요구사항 및 API 계약, 오류 경계, 데이터 무결성, 보안, 불필요한 의존성, 테스트 독립성, 변경 범위를 확인하고 발견한 결함은 회귀 케이스와 함께 수정한다.
8. `qa/REPORT_TEMPLATE.md`를 사용해 `qa/reports/RS-010.md`를 작성하고 `qa/TEST_CASES.csv`에서 자신의 케이스 상태를 갱신한다. `tickets/RS-010.md` 및 INDEX의 완료 증거도 기록한다. 실행되지 않은 외부 환경 검증은 NOT RUN/BLOCKED로 남긴다.
9. 기존 완료 조건과 TEST_PLAN의 품질 게이트를 모두 충족할 때만 DONE으로 판단한다. 실제 Git 권한이 있을 때만 자기 변경을 커밋하고 push/merge/후속 티켓 착수는 하지 않는다.

## 완료 판정
- [ ] 홈 화면 추가 동작 검증.
- [ ] 정적 파일 외 캐시 및 민감 정보 저장 금지.
- [ ] 오프라인 요청 실패 명확히 표시 및 자동 재전송 없음.
- [ ] 기존 기능/보안 회귀 없음.

위 조건을 증거로 검증한 후 `python -m pytest -q`와 `git diff --check`를 실행하라. 실행 불가/실패는 사실대로 기록하라. `tickets/RS-010.md`와 `tickets/INDEX.md`의 상태와 완료 보고를 갱신하라. Git 작업이 허용될 때 브랜치 `feature/RS-010-pwa`에서 자기 변경만 `feat(pwa): support home screen installation (RS-010)` 형식으로 커밋하라. 후속 티켓은 자동 시작하지 마라.

## 인계
PWA 미적용 MVP와의 차이, 브라우저 설치 검증 및 캐시 정책을 운영 문서에 전달.

`prompts/COMMON.md`의 완료 보고 형식으로 최종 답변하라. 확인되지 않은 정책이나 환경 검증은 완료라고 주장하지 마라.
