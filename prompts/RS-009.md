# RS-009 실행 프롬프트

당신은 RoomShare 프로젝트의 소프트웨어 개발 Agent다. 현재 저장소에서 **RS-009 — 통합 테스트 및 릴리스**만 실제 구현하라. 단순 설계 제안이나 코드 예시만 작성하지 말고, 필요한 파일을 수정하고 테스트를 실행하라.

## 먼저 읽을 파일
`AGENTS.md`, `README.md`, `docs/REQUIREMENTS.md`, `docs/DECISIONS.md`, `docs/DESIGN.md`, `docs/API.md`, `docs/DEPLOYMENT.md`, `tickets/INDEX.md`, `tickets/RS-009.md`, `prompts/COMMON.md`.
공통 작업 지침을 적용하며 선행 티켓(RS-008)의 실제 완료 및 산출물을 검증하라. 사용자 변경 보존 및 테스트 전용 DB 사용. 운영 서버 변경/push/merge 금지.

## 이번 작업의 목표
MVP의 기능/동시성/보안/복구를 통합 검증하고 릴리스 가능 여부를 판정한다.

## 수행할 작업
1. FR-01~13/NFR-01~04를 테스트와 연결하는 추적표 작성. 확정/임시 정책 및 제외 기능 구분. RS-001~008의 미완료 필수 항목과 코드/테스트 차이를 조사한다. OCI 미검증이 선행 차단이면 릴리스는 BLOCKED로 유지하고 가능한 로컬 검증만 수행(별도 승인 또는 티켓 인계 기록).
2. 깨끗한 venv/임시 DB에서 전체 테스트, 마이그레이션 및 사용자 생성/충돌/취소/재예약/관리자 수정/차단/로그/설정 통합 시나리오 실행.
3. 별도 연결 동시 예약, 일부 충돌 rollback, DB busy 처리, 날짜 경계, 재시작 데이터 유지 검증. 결과 DB에서 상태/점유/이력 일관성 확인.
4. 관리자 호스트/인증서/위조 헤더/직접 백엔드/Origin/CSRF, CORS/제한, 개인정보/토큰 누출, XSS 입력, 비밀 파일 추적 여부 확인. 프록시 종단 테스트를 앱 단독 테스트와 구분한다.
5. 모바일 Safari/Chrome 실제 장치 또는 이용 가능한 브라우저로 360px 포함 검사. 에뮬레이션과 실제 장치를 구분한다. 실제 OCI 리소스는 접근 가능할 때만 CPU/RAM/디스크/로그/재시작 및 백업 복원 기록.
6. 릴리스 체크리스트에 운영 정책 승인(DECISIONS), 접근 제어, DNS/TLS, 백업/복원, 장애 rollback, 실제 환경 테스트 포함. 심각한 보안/데이터 손실/미승인 공개 조건이 있으면 NO-GO. 운영 배포/태그/push를 자동 수행하지 않는다. PWA는 MVP 범위 아님.

## 변경 범위
tests/integration/, tests/manual/, docs/RELEASE_CHECKLIST.md, docs/TEST_REPORT.md, README.md, tickets/INDEX.md
파일명은 제안이며 실제 저장소 구조에 맞추되 범위를 확대하지 마라.

## 테스트 요구
- 전체 pytest 결과와 실패/skip/미실행 건수.
- 깨끗한 설치 및 DB 재시작/백업 복구 통합 시나리오.
- 사용자/관리자 권한 매트릭스 및 실제 프록시 검증.
- FR/NFR별 PASS/FAIL/NOT RUN 증거, 브라우저/OS/실행 환경 명시.
- 정책/실제 OCI/보안 결함이 남은 경우 NO-GO 판정 및 재검증 계획.

## 심화 실행 절차 (v2)
반드시 `docs/TEST_PLAN.md`, `qa/specs/RS-009.md`, `qa/REPORT_TEMPLATE.md`, `qa/TRACEABILITY.md`를 추가로 읽어라. 다음 지침은 기존 티켓의 구현 범위와 함께 적용한다.

1. 새 기능을 추가하지 말고 RS-001~008의 변경 이력과 실제 테스트 증거를 리뷰한다. 요구사항 ID별 테스트 매핑과 결과를 갱신하며 실패 재현 케이스를 먼저 추가한 뒤 결함을 수정하거나 해당 티켓으로 반환한다.
2. 테스트 순서: 정적 검사 → 단위/DB → API/통합 → 동시성 → 실제 브라우저 → 프록시/배포/복구 → 성능 기준선 → OCI → 승인 게이트. 새 DB 및 별도 합성 데이터만 사용한다.
3. 성능은 idle/부하 CPU·RSS·디스크, 요청별 p50/p95/p99, 예상 409 및 429와 예상외 5xx 구분, 요청 수/동시성/시간을 기록한다. 환경 미확정이므로 수치 목표는 제안이며 승인 없이 합격 기준으로 고정하지 않는다.
4. 릴리스 후보 commit과 테스트 실행 commit이 같아야 한다. 필수 변경 후 해당 테스트 및 전체 회귀를 재실행한다. 실제 기기/OCI 미검증은 명시적 릴리스 차단 항목으로 기록한다. GO/NO-GO 판단과 실제 공개 승인은 별개다.

### 구현 및 테스트 수행 순서
1. 선행 산출물과 현재 코드를 확인하고 이번 티켓의 파일/인터페이스/테스트 계획을 작성한다. 아직 구현되지 않은 후속 기능은 범위에 넣지 않는다.
2. 다음 명세를 기준으로 가능한 자동화 테스트를 작성한다. 미구현 기능의 실패 또는 기존 기준선을 실제 실행하고, 테스트의 실패 이유를 기록한다. 존재하지 않는 테스트를 실행했다고 주장하지 않는다.
3. 기능을 구현하고 정상/오류/경계 케이스를 반복 실행한다. 실제 SQLite가 필요한 테스트에 mock DB를 쓰지 않는다. 수동 케이스는 실제 환경에서만 PASS 처리한다.
4. 명세의 기대 결과를 상태·응답·DB/로그 등 해당 관찰 지점에서 직접 검증한다. 관련 TC ID를 테스트명, 파라미터 ID 또는 보고서에 연결한다.
5. 아래 목록 전체와 상세 명세의 사전 조건·절차를 확인한다. 케이스를 임의 삭제하거나 skip으로 통과시키지 않는다.
- `TC-009-01` [e2e/local] 사용자 전체 시나리오 → 원룸 단일 점유, 개인 정보 비노출, 재예약 성공
- `TC-009-02` [e2e/local] 관리자 전체 시나리오 → UI/API/DB 일치, 실패 변경 없음
- `TC-009-03` [concurrency/local] 릴리스 동시성 회귀 → 충돌 정책과 원자성, 성공 수/점유/로그 불변식 확인; timeout 구분
- `TC-009-04` [integration/local] 장애 및 날짜 경계 회귀 → 정책 일치, 모든 실패 롤백
- `TC-009-05` [security/local] 접근 제어 회귀 → 우회 없음, 공개 사용자 권한만 보유
- `TC-009-06` [security/local] 민감 정보 및 입력 보안 → 예외인 본인 토큰 1회 외 비밀 노출 없음, XSS/SQL 삽입 없음
- `TC-009-07` [recovery/local] 깨끗한 설치에서 복구 → 기존 데이터 유지 및 복원 일치
- `TC-009-08` [manual/device] 모바일 최종 회귀 → 각 플랫폼 결과, 한계 및 재검증 계획 기록
- `TC-009-09` [performance/local] 경량 서버 부하 기준선 → p50/p95/p99, 오류율, RSS/CPU/DB 크기 및 설정 기록; 409는 예상 경쟁 결과로 분리
- `TC-009-10` [deploy/oci] OCI 최종 스모크 → 실제 OCI 증거; 미접속은 NOT RUN, 공개 릴리스 NO-GO
- `TC-009-11` [review/local] 추적성과 보고서 → 모든 요구사항 연결, 필수 FAIL/NOT RUN/SKIP 식별, 허위 PASS 없음
- `TC-009-12` [review/approval] 릴리스 게이트 → 필수 미검증·정책 미승인·보안 결함 시 NO-GO; 자동 공개 금지
6. 대상 테스트 및 전체 pytest를 실행하고 결과/종료 코드/수집 건수/실패·skip을 기록한다. 브라우저, Nginx, OCI 등 별도 테스트는 실제 명령 및 환경 증거를 남긴다.
7. 자기 변경에 대한 코드 리뷰를 수행한다. 요구사항 및 API 계약, 오류 경계, 데이터 무결성, 보안, 불필요한 의존성, 테스트 독립성, 변경 범위를 확인하고 발견한 결함은 회귀 케이스와 함께 수정한다.
8. `qa/REPORT_TEMPLATE.md`를 사용해 `qa/reports/RS-009.md`를 작성하고 `qa/TEST_CASES.csv`에서 자신의 케이스 상태를 갱신한다. `tickets/RS-009.md` 및 INDEX의 완료 증거도 기록한다. 실행되지 않은 외부 환경 검증은 NOT RUN/BLOCKED로 남긴다.
9. 기존 완료 조건과 TEST_PLAN의 품질 게이트를 모두 충족할 때만 DONE으로 판단한다. 실제 Git 권한이 있을 때만 자기 변경을 커밋하고 push/merge/후속 티켓 착수는 하지 않는다.
