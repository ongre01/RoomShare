# RS-008 실행 프롬프트

당신은 RoomShare 프로젝트의 소프트웨어 개발 Agent다. 현재 저장소에서 **RS-008 — Ubuntu/OCI 배포 및 백업**만 실제 구현하라. 단순 설계 제안이나 코드 예시만 작성하지 말고, 필요한 파일을 수정하고 테스트를 실행하라.

## 먼저 읽을 파일
`AGENTS.md`, `README.md`, `docs/REQUIREMENTS.md`, `docs/DECISIONS.md`, `docs/DESIGN.md`, `docs/API.md`, `docs/DEPLOYMENT.md`, `tickets/INDEX.md`, `tickets/RS-008.md`, `prompts/COMMON.md`.
공통 작업 지침을 적용하며 선행 티켓(RS-005,RS-007)의 실제 완료 및 산출물을 검증하라. 사용자 변경 보존 및 테스트 전용 DB 사용. 운영 서버 변경/push/merge 금지.

## 이번 작업의 목표
개인 Ubuntu에서 검증 가능한 배포 패키지를 만들고 OCI 이전 절차와 검증을 분리한다.

## 수행할 작업
1. 개발 Ubuntu와 OCI의 Python/OS/RAM/디스크/네트워크/권한을 구분하여 실제 확인 가능한 항목만 기록. 운영 경로 /opt/roomshare, /var/lib/roomshare, /etc/roomshare, 비권한 서비스 계정, DB/설정 권한, venv lock 설치 및 명시적 마이그레이션. 환경별 설정 예제를 작성하고 실제 키/인증서/비밀은 포함하지 않는다.
2. systemd unit은 단일 worker, loopback 또는 권한 제한 Unix socket, 재시작 정책, 로그, 작업 디렉터리, 환경 파일 및 최소 쓰기 경로 구성. 백엔드 포트 외부 공개 금지. 배포 스크립트는 실패 시 nonzero, 오류 출력, 재실행 안전성을 확보한다. 실행 중 데이터베이스를 덮어쓰지 않는다.
3. Nginx 사용자/관리자 vhost 별도, HTTPS, HTTP 처리, 기본/알 수 없는 호스트 거부, 사용자 호스트 관리자 UI/API 차단. 관리자 호스트 mTLS 검증 성공 후에만 접근 신호를 전달한다. 사용자 입력의 내부 헤더 및 Forwarded 헤더는 제거/덮어쓴다. 앱 guard와 동일 계약. 요청 크기/빈도 제한, 민감 응답 캐시 방지, TLS 개인키 및 CA 관리/폐기 문서. mTLS 대신 사설망 선택은 별도 승인 전 임시 변경 금지.
4. 인증서/DNS 예시는 템플릿으로 표시. 테스트용 CA/client cert는 별도 임시 경로에서만 생성. nginx -t 및 로컬 TLS 경로 테스트; 운영 설정을 자동 reload하지 않는다. OCI 보안 목록/NSG/OS 방화벽과 SSH 관리 IP, 443/필요 시 80만 허용, 실제 변경은 운영자 승인 필요.
5. SQLite backup API 또는 sqlite3 .backup으로 일관된 스냅샷 생성, 권한 제한, 실패/무결성 검증, 일일 timer, 보존 기간 설정(이력 90일과 백업 보존 정책은 서로 구분하고 미확정 명시). WAL 파일 단순 복사 금지. 복원은 임시 DB에 먼저 검증, 운영 복원은 서비스 정지/기존 DB 보존/명시적 확인 후 수행.
6. 로컬 배포 → 테스트 → OCI 이전 계획. 배포 전 백업, 릴리스 버전/lock, DB 스키마 호환성 점검, 상태 확인, 이전 코드+호환 DB로 rollback 절차. 실제 OCI 권한 없으면 접속/배포/성능 검증을 NOT RUN으로 표시.

## 변경 범위
deploy/nginx/, deploy/systemd/, scripts/install.sh, scripts/deploy.sh, scripts/backup.sh, scripts/restore.sh, docs/DEPLOYMENT.md, deploy/README.md, tests/test_backup_restore.py
파일명은 제안이며 실제 저장소 구조에 맞추되 범위를 확대하지 마라.

## 테스트 요구
- shell syntax 및 가능한 경우 systemd-analyze verify, nginx -t(실제 명령 결과).
- 로컬 HTTPS 테스트: 사용자 접근, 사용자 Host 관리자 차단, 관리자 인증서 없음/잘못된 CA 거부, 유효 cert 정상, 위조 내부 헤더 거부, 미등록 호스트 차단.
- 외부 인터페이스 백엔드 직접 접속 실패(실제 환경별 검증), 서비스 재시작 후 예약 유지.
- WAL 사용 중 백업 생성/무결성 확인/격리된 경로 복원 후 예약 및 설정 비교, 손상 백업 복원 거부.
- 설치/배포 스크립트 오류 처리, 운영 복원 보호, 재실행 검증.
- OCI DNS/TLS/네트워크/실제 자원 검증은 접근 시만 실행.

## 심화 실행 절차 (v2)
반드시 `docs/TEST_PLAN.md`, `qa/specs/RS-008.md`, `qa/REPORT_TEMPLATE.md`, `qa/TRACEABILITY.md`를 추가로 읽어라. 다음 지침은 기존 티켓의 구현 범위와 함께 적용한다.

1. 설치, 구성 생성, 마이그레이션, 서비스 전환, 검증, 롤백 단계를 분리한 runbook을 작성한다. 기존 설치를 다시 실행할 때 DB/환경 설정/인증서 덮어쓰기 금지. 실제 sudo/systemd/Nginx 변경은 승인된 스테이징에서만 수행한다.
2. Nginx 테스트는 운영 config가 아닌 격리 config와 테스트 CA로 수행한다. 실제 Host/SNI, 프록시가 덮어쓴 헤더 및 앱 guard를 함께 검증한다. 외부 백엔드 차단은 별도 클라이언트에서 측정한다. 실제 인증서 만료/갱신/폐기 절차는 운영자 승인 필요.
3. backup은 일관된 SQLite snapshot으로 생성하며 임시 파일에 기록 후 검증 성공 시에만 최종 이름으로 이동한다. 소유권/권한, 실패 로그, 보존 기간, 별도 위치 및 복구 순서를 작성한다. 복원 대상은 기본 임시 경로이며 운영 복원은 확인/정지/원본 보존/검증이 선행되어야 한다.
4. 배포 결과를 LOCAL-STAGING과 OCI로 분리한다. 환경 차이, 실제 DB/인증서 이동 방법, downtime 및 이전 릴리스 호환성을 점검한다. 실제 운영 데이터 또는 키를 Agent 산출물로 복사하지 않는다.

### 구현 및 테스트 수행 순서
1. 선행 산출물과 현재 코드를 확인하고 이번 티켓의 파일/인터페이스/테스트 계획을 작성한다. 아직 구현되지 않은 후속 기능은 범위에 넣지 않는다.
2. 다음 명세를 기준으로 가능한 자동화 테스트를 작성한다. 미구현 기능의 실패 또는 기존 기준선을 실제 실행하고, 테스트의 실패 이유를 기록한다. 존재하지 않는 테스트를 실행했다고 주장하지 않는다.
3. 기능을 구현하고 정상/오류/경계 케이스를 반복 실행한다. 실제 SQLite가 필요한 테스트에 mock DB를 쓰지 않는다. 수동 케이스는 실제 환경에서만 PASS 처리한다.
4. 명세의 기대 결과를 상태·응답·DB/로그 등 해당 관찰 지점에서 직접 검증한다. 관련 TC ID를 테스트명, 파라미터 ID 또는 보고서에 연결한다.
5. 아래 목록 전체와 상세 명세의 사전 조건·절차를 확인한다. 케이스를 임의 삭제하거나 skip으로 통과시키지 않는다.
- `TC-008-01` [deploy/local] 배포 스크립트 정적 검사 → 각 종료 코드 기록; 미설치 도구는 NOT RUN
- `TC-008-02` [deploy/local] 설치/재실행 → 데이터/설정 보존, 실패 nonzero, 중간 성공으로 보고하지 않음
- `TC-008-03` [deploy/local] 서비스 최소 권한 → root 아닌 계정, loopback/제한 Unix socket, 허용 경로만 쓰기
- `TC-008-04` [security/local] 사용자 TLS 및 관리자 차단 → 유효 TLS, 공개 기능 정상, 관리 경로 차단
- `TC-008-05` [security/local] mTLS 인증서 행렬 → 유효한 인증서만 관리자 접근, 나머지 handshake 또는 HTTP 거부
- `TC-008-06` [security/local] 프록시 헤더 위조 → 외부 위조로 관리자 권한 획득 불가; 실제 신뢰 경계 확인
- `TC-008-07` [security/local] 호스트/경로 우회 → 관리 기능 및 민감 정보 노출 없음; 기본 호스트 거부
- `TC-008-08` [security/local] 백엔드 직접 접근 → 외부에서 접근 불가; 로컬 app test와 구분
- `TC-008-09` [security/local] 프록시 제한 및 캐시 → 크기 초과 거부, 빈도 429 계약 일치, 토큰/관리 데이터 캐시 없음
- `TC-008-10` [recovery/local] 재시작 지속성 → 스냅샷 일치, healthz 정상, 권한 유지
- `TC-008-11` [recovery/local] WAL 온라인 백업 → 일관된 시점의 스냅샷, integrity_check=ok/FK 위반 0, 유령 데이터 없음
- `TC-008-12` [recovery/local] 손상 백업 거부 → 정상만 복원, 손상본 nonzero, 기존 목적지 보호
- `TC-008-13` [recovery/local] 복원/롤백 보호 → 무승인 변경 금지, 이전 릴리스 및 데이터 검증, 실패 시 원본 보존
- `TC-008-14` [deploy/local] 자동 백업 및 보존 → 정상 백업만 정리 대상, 최신 검증 백업 유지, 실패 기록
- `TC-008-15` [deploy/oci] OCI 실제 배포 검증 → 실제 결과가 로컬과 별도 기록, 접근 없으면 NOT RUN
- `TC-008-16` [performance/oci] 운영 자원 측정 → 환경/샘플 수/p95/오류율 기록, 합의 기준과 비교; 목표 미확정이면 기준 미확정 표시
6. 대상 테스트 및 전체 pytest를 실행하고 결과/종료 코드/수집 건수/실패·skip을 기록한다. 브라우저, Nginx, OCI 등 별도 테스트는 실제 명령 및 환경 증거를 남긴다.
7. 자기 변경에 대한 코드 리뷰를 수행한다. 요구사항 및 API 계약, 오류 경계, 데이터 무결성, 보안, 불필요한 의존성, 테스트 독립성, 변경 범위를 확인하고 발견한 결함은 회귀 케이스와 함께 수정한다.
8. `qa/REPORT_TEMPLATE.md`를 사용해 `qa/reports/RS-008.md`를 작성하고 `qa/TEST_CASES.csv`에서 자신의 케이스 상태를 갱신한다. `tickets/RS-008.md` 및 INDEX의 완료 증거도 기록한다. 실행되지 않은 외부 환경 검증은 NOT RUN/BLOCKED로 남긴다.
9. 기존 완료 조건과 TEST_PLAN의 품질 게이트를 모두 충족할 때만 DONE으로 판단한다. 실제 Git 권한이 있을 때만 자기 변경을 커밋하고 push/merge/후속 티켓 착수는 하지 않는다.
